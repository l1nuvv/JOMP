## Runtime components
- `PeelGame` remains the scene component and public facade. It owns serialized references, economy fields, route/session timing and Unity callbacks; it wires the plain C# subsystems at startup.
- `PeelInteractionController` owns the grip, target selection, working strips and stacks, layer advancement and release gating. `PeelAudioController` owns the loop, detach accent, fades and area-music mix.
- `PeelScreenController` owns the current screen, application focus and Starter Assets cursor/look synchronization. `PeelGameUI` owns IMGUI rendering, menu selection and notices; it reads live session state and invokes actions through `IPeelGameUIState`.
- `PeelProgressionController` owns purchase and reward rules, operating on the existing economy fields by reference. `PeelSaveCoordinator` owns save inspection, validation, migration, recovery and persistence status. The facade still decides when to save and applies loaded economy and player state.
- PeelSettings: EN/RU UI table, paired notice material sets, wall-text translation, sound/sensitivity preferences and change notification. Settings apply immediately; PlayerPrefs stores preferences only.
- PeelPosterStack: authored depth per patch, initial front/back notice designs and a deterministic older-design sequence. Two four-strip buffers are reused; logical depth is integer state. A combined mesh contains deeper sheets; its non-convex MeshCollider blocks targeting through visible lower paper. The collider is rebound when the mesh changes and disabled when empty.
- PeelStrip: reusable deformable geometry, cached renderer/collider, idempotent removal within the current poster. An underlying buffer cannot become exposed through a missing front strip.
- PeelScrapPool: 32 preallocated meshes/objects with no colliders. Starter tearing emits strips; an intact scraper/steam poster emits one full-sheet visual. A partly torn poster retains its missing parts.
- PeelPosterOutline: one closed LineRenderer around the whole reachable top poster under the ray. Occluded/out-of-range targets and menus clear selection.
- PeelToolView: three Blender-authored prefab views (card, scraper, steam), selected by upgrade/tool state. Shared imported meshes/materials; steam particles at the nozzle.
- PeelWorkbench: marker on the imported tool-cart collider.
- StarterAssets.FirstPersonController / StarterAssetsInputs: existing movement, look, cursor and focus integration.
## Invariants
One grip captures one strip with the card, a whole front poster with the scraper, or up to three visible nearby front posters with steam (up to five after the experimental wider-steam purchase). Holding LMB may start another grip after a fresh reach/occlusion raycast. Release is still required after a menu transition or tool switch.
Paper payout is $2 per removed part; a complete fresh poster pays $8. Partly paid posters only pay for remaining parts.
Advance a stack only after every front part is detached and after the active grip references are cleared. New layers reuse display buffers and synchronize physics once after advancement.
Cursor ownership is synchronized with StarterAssetsInputs. Menus keep the cursor free; gameplay locks it; active peeling holds the camera steady until release.
Runtime paper discovery occurs at startup. Steam selects from cached stacks through the spatial grid for neighbour lookup. Materials refresh on language changes or buffer reuse.
## Authoring and verification
PeelProgressionSetup configures the existing scene's stack buffers, paired languages and starter card, then removes the decorative bench. It is a deliberate migration, not a routine check.
PrototypeBuilder, ArtRevision and StreetArtPass are historical helpers. StreetArtPass rejects a live poster-stack scene; do not use them to regenerate it. Preserve GUIDs and the original combined-shell/collider split.
PeelProgressionChecks is an Editor/MCP runtime check, not player-facing functionality. It uses a temporary virtual Input System keyboard and restores settings/removes the device afterward. The older SourceArt/StreetRevision/verify_playmode.cs.txt checks the superseded two-layer implementation and must not be run against the new stack system.
## Known debt
UI remains IMGUI prototype. `ThreeAreaPrototype` has a versioned world autosave with stable stack IDs and partial strip progress. Schema 2 uses the fixed route key `three-area` and keeps the existing filename so it can read schema 1. Schema 1 accepts the original scene path and maps the old grouped courtyard door IDs to explicit current IDs. New scene paths need no migration under schema 2. Future stack splits or removals require an explicit versioned ID map that accounts for completed sheets and partial strips. Unknown versions and routes are preserved and require explicit reset to start a new shift. If the primary is corrupt and the backup validates, recovery keeps the damaged primary alongside the restored file. Review mode bypasses world persistence.

`MainRoute` has a separate `main-route` save key and `main-route-save-v1.json` file. Its serialized route boundaries drive both gameplay and the Continue location label. The scene keeps its placed furniture and activates the placed final note and spotlight when the required archive stacks are clear. Legacy route migrations apply to the `three-area` slot.

`MainRoute` persists the completed glass encounter as the optional boolean `basementGlassSeen`. Missing values in older slots leave the event eligible. After completion, Continue restores the sheet on the far side of the pane. The encounter checks the view ray and active basement light, then runs beside the normal player controls. The newer story prints are fixed in new shifts. Previously saved print assignments still resolve through their saved palette.

`PavilionMural` uses route key `pavilion` and file `pavilion-save-v1.json`. Stable `pavilion.bay*` stack IDs restore completed sheets and the current strip progress. The HUD derives remaining sheets from restored stack counts. In this slot `lightOn` records the final switch. Save validation requires all sheets clear when the light is on. Activating the switch checkpoints both copies through the existing save coordinator.

`PavilionHub` uses route key `pavilion-hub` and file `pavilion-hub-save-v1.json`. It reuses the pavilion stacks and switch. The existing `paper` payload holds bundle capacity, items and undelivered value, and a successful hand-in checkpoints bundle and balance together. The shop keeps the pavilion's paid tool progression. The archive paper trial uses its own slot and controls.

`PeelNoticeLayout` assigns ordinary prints once per new scene session from the `PeelSettings` palette. It favours lower counts within each print format and penalizes repeats between consecutive layers and same-depth sheets in nearby stacks. Physical dimensions still come from the authored layer. Blank backing and `PeelGame` story references keep their placed designs. Ordinary stacks need no layout configuration.

New saved shifts use v5. The slot stores a material-name palette and the chosen indices per stable stack ID and layer. Continue resolves that palette and restores the prints before partial strips and the cabinet. Material names used by supported saves are persistent identifiers. Saves v3 keep the scene-authored layout. `PavilionHub` v4 keeps its original lower-print table, and those slots continue writing their existing version. The cabinet resolves each cleared sheet to the shared RU/EN texture name and records the bays where that print was found.

Load restores route geometry and lighting before checking the saved player capsule. Blocked or unsupported positions fall back to the scene spawn while keeping the loaded progress. Player build persistence, gamepad verification, human mouse feel, final pacing and artistic acceptance remain separate from method-level checks.
